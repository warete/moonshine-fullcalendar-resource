# FullCalendar refresh event target mismatch

**Date:** 2026-02-26 20:20
**Files:** resources/js/full-calendar.js
**Severity:** high

## Problem

Calendar auto-refresh after modal CRUD was implemented but likely did not trigger.
The Alpine component listened for `fullcalendar:refresh` on `document`, while MoonShine dispatches response events through global `dispatchEvent(...)` (window target).

Manual refresh via `window.fullCalendarRefresh()` was also inconsistent because it still emitted the legacy `moonshineFullCalendarRefresh` event and did not trigger the new listener.

## Root Cause

The implementation assumed MoonShine custom events were dispatched on `document`.
In MoonShine they are dispatched via the global `dispatchEvent(...)`, which targets `window`.

Additionally, the manual helper was not updated when the refresh mechanism moved to `fullcalendar:refresh`, so documentation and helper behavior drifted apart.

## Solution

- Registered the refresh listener on `window` (actual MoonShine dispatch target)
- Kept a `document` listener too for compatibility with custom/manual dispatches
- Treated missing `detail.resource` as a broadcast refresh so `window.fullCalendarRefresh()` can refresh all calendars
- Updated `window.fullCalendarRefresh()` to dispatch `CustomEvent('fullcalendar:refresh', { detail })`
- Added fix-specific logs with `[FIX]` prefix for verification/debugging

## Prevention

- When integrating with framework UI events, verify the actual dispatch target (`window` vs `document`) in vendor source before wiring listeners
- Keep helper APIs and README examples synchronized when changing event names/payloads
- Add a small frontend regression check for event dispatch/listener compatibility (listener target + event name + payload shape)
