# FullCalendar day range query returned wrong day due to raw ISO8601 SQL comparison

**Date:** 2026-02-26 20:42
**Files:** src/Resources/FullCalendarResource.php
**Severity:** critical

## Problem

`timeGridDay` requested a day range (e.g. `2026-02-26T00:00:00.000Z` → `2026-02-27T00:00:00.000Z`),
but the backend returned events from the next day (`2026-02-27` daytime hours). Frontend parsed them
correctly, but they did not overlap the requested day, so nothing rendered in `timeGridDay`.

## Root Cause

The query filter used raw ISO8601 strings from FullCalendar directly in Eloquent `whereBetween` against
database datetime columns. Comparing DB datetime columns to ISO8601 (`T...Z`) strings is DB-dependent and
can produce incorrect filtering results.

Additionally, FullCalendar's `end` boundary is exclusive, but the original overlap logic was fully inclusive.

## Solution

- Normalize `start/end` query boundaries to DB-friendly `Y-m-d H:i:s` via `Carbon`
- Apply overlap filtering using FullCalendar semantics: `[start, end)` (exclusive end)
- Add `[FIX][query-range]` logs for raw vs normalized boundaries
- Keep fallbacks for records with missing/legacy `end` values

## Prevention

- Never pass frontend ISO8601 query strings directly into SQL datetime comparisons
- Normalize request datetime boundaries at the server boundary layer before building queries
- Align SQL overlap logic with FullCalendar's exclusive `end` semantics
