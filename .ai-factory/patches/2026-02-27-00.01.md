# Use resource `findItem()` and MoonShine save pipeline for calendar date mutations

**Date:** 2026-02-27 00:01
**Files:** src/Resources/FullCalendarResource.php
**Severity:** medium

## Problem

The first implementation of calendar drag/resize date updates introduced two behaviors
the user did not want:

- explicit access checks in `authorizeCalendarEventDatesUpdate(...)`
- direct model persistence (`$item->save()`) inside the package default hook

It also resolved the event via a raw model query instead of the resource's own item
resolution path.

## Root Cause

The default implementation optimized for a standalone package path and added policy
checks + direct Eloquent save for simplicity. This bypassed part of MoonShine resource
behavior and made the package less aligned with the requested extension model.

## Solution

- Removed `authorizeCalendarEventDatesUpdate(...)` and its invocation.
- Updated `resolveCalendarEventForDateUpdate(...)` to resolve the record via
  `setItemID(...) + findItem(orFail: true)` and then extract the model from the wrapper.
- Updated `applyCalendarEventDateUpdate(...)` to call MoonShine resource `save(...)`
  (after setting `item`, `itemID`, and active form page when available) instead of
  calling `$item->save()` directly.
- Added `[FIX][date-update]` logs for the new resolution/persistence path.

## Prevention

- For package resource mutations, prefer resource-native retrieval/persistence hooks
  (`findItem`, `save`) before using raw model queries/saves.
- Confirm with the user whether authorization belongs in the package layer or in the
  consuming resource/application layer before adding policy checks.
- Keep the package default path override-friendly and as close as possible to MoonShine's
  own lifecycle.
